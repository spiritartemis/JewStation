# 用例管理方案（QA cases）

一套用例 = **两个文件**，一稳一变：

```
<仓>/blueprint/qa/<板id>-<里程碑id>.cases.md     用例本体（稳定；改判据才动）
<仓>/blueprint/qa/<板id>-<里程碑id>.runs.md      跑测留痕（只追加；每次跑一轮加一节）
```

为什么拆两份：用例是**契约**（该验什么，改一次要过评审），跑测是**事实**（今天过了、下周红了）。
把两者写在一份里，状态一 update 就把「原本要求什么」覆盖掉了。

> 需求级（无里程碑）的单点验收：`<板id>-<需求id>.cases.md`，同一套规则。

## 1. 用例 id

```
QA-<板id>-<里程碑id>-<NN>        例：QA-gm-m4-01
```

- 板 id 进 id 的理由：同一台机器多块板（自举板 / 项目板）会有同名里程碑，光一个 `m4` 分不清。
- **id 不复用**：用例废了写 `状态: retired` 并留一行为什么，不腾号。

## 2. 每例的六个字段（缺一个就不算写完）

| 字段 | 写法要求 |
|---|---|
| **覆盖** | 指到版本 `x.y` + 需求 id（`R-…` / `B-…`）。指不到需求的用例 = 没人认领的用例 |
| **目的** | 一句话，说清「验的是哪条承诺」。写「验证功能正常」等于没写 |
| **步骤** | 可复制的命令，带沙箱前置与期望的环境（哪块板、哪棵树） |
| **判据** | pass 的观察点，**逐条落到账**（见 §3） |
| **易漏** | 反例：这条最容易假绿的那一种跑法。这是用例的灵魂，不是备注 |
| **人工项** | 有 → 引用 `manual-actions.md` 的票号（`A1`…）；没有 → 写 `—` |

## 3. 判据三档（必须标明是哪一档）

| 档 | 形态 | 谁判 |
|---|---|---|
| **断言** | 账里出现/不出现某行、输出 exit 非 0、`--json` 字段取值 | agent 可判，可写成机检 |
| **观察** | 文案是否指对路、提示是否说清下一步、渲染是否显示该段 | agent 可判，但**要贴原文片段**当证据 |
| **人判** | 好不好用、像不像样、这个取舍认不认 | 只进人工清单，agent 不代判 |

「观察」档的红必须贴原文；贴不出原文的结论不算证据。

## 4. 状态五态（写在 cases 文件的索引表里）

| 状态 | 含义 |
|---|---|
| `pending` | 还没跑 |
| `pass` | 判据逐条成立，证据在 `runs.md` |
| `fail` | 有判据不成立，且已归因 `真缺陷`（带缺陷 id 或建议定级） |
| `expected` | 现象与设计稿一致（例如字段未回填）⇒ **不算通过也不算失败**，附设计稿出处 |
| `blocked` | 前置缺失（环境 / 依赖未落地 / 沙箱不合规），不判对错 |

`expected` 这一态是本方案的核心：**没有它，所有「设计上就该空」的项都会被报成红**，几轮之后没人再看报告。

## 5. runs.md 一节长什么样

```
## <日期> · <执行者> · 板 <板id> · 里程碑 <里程碑id>
环境：<OS / node 版本 / 沙箱根 / CLI 入口>
基线：gd contract check --scope all ⇒ ok|warn|fail；相关 e2e ⇒ 套件名 + 退出码

| 用例 | 结论 | 证据（账行 / 输出片段 / 套件） | 分类 |
|---|---|---|---|
| QA-gm-m4-01 | pass | index.yaml:41 context[] 三条 … | — |
| QA-gm-m4-07 | fail | …（原文） | 真缺陷 → 建议 B 单 minor |

人工项：A1 / A3（见 manual-actions.md）
结论：具备 / 不具备 结版条件 + 一句话理由
```

## 6. 与 e2e 的分工（别互相冒充）

| 层 | 是什么 | 谁跑 |
|---|---|---|
| `*-e2e.mjs` | 机检回归：钉住**已有**行为，快、可 CI | 每次改代码 |
| QA 用例 | 端到端可人读：一条承诺走完全程，能验「指引自洽 / 读面同源 / 真拒单」 | 结版前一轮 |

用例允许**引用 e2e 作证据**（写清套件名 + 退出码），但一条用例不能只有 e2e 证据——
至少一条判据是端到端走出来的（否则 e2e 绿而流程不通时，用例也绿）。

## 7. 归档

- 里程碑 `reached` 后：`cases.md` 与 `runs.md` 一起挪 `archive/qa/`，index 表的最终状态随件保留。
- 新开的里程碑**不复制旧用例**：从 `case-scheme` 的六字段重写（旧用例的判据是旧承诺）。

## 8. 反模式（见到就退回重写）

- 判据写成「执行成功 / 无报错 / 页面正常」
- 用真板造陪跑数据（污染进度面，且下一轮 `brief` 会读错）
- 只跑 happy path（没有一条用例是「故意违规应该被拒」）
- 把 `expected` 当垃圾桶（设计稿指不出出处的，不许标 expected）
- 一份用例同时验 5 条不相干的承诺（红了不知道是哪个坏了，绿了不知道哪个没坏）
