# 纪律：开版 / 结版 / 缺陷分档 / 模式闸 / 边界

## 0. 板是什么

一块**板** = 账的落点 + 编号命名空间。只有两样东西要紧：

- **板根**：`<git-common-dir>/gdtwork`（缺省）。worktree 共享、不进任何提交 ⇒ 并行会话看到同一份 live 账。
  另有 `--in-tree`（落仓根，账随代码同仓）与 `--board-dir <路径>`（显式）两种摆法。
- **板 id**：编号前缀。需求 `R-<板id>-001`、缺陷 `B-<板id>-001`、任务 `T-<板id>-001-01` 都由它派生。

**板实分离**：账在板根，代码在仓里（`board.yaml: repo` 是交付件与路径的基准）。

## 0.2 命令落在哪本账

板上的命令**缺省就落本仓的板**（不必逐条加 `--board`）：`req new` / `task add` / `handoff` / `check` / `milestone …` / `ver …`。
要动**注册项目账**（`projects/<name>/`）必须显式 `--project <项目id>`；`--board` 仍可用但只是兼容别名。
环境里没有板（未 `core init` 的仓）时回落注册表当前项目并打一行提示。

## 0.5 开版纪律（铁律 · 先读这一段）

排期分成**两轴**，只有**两层是实体**：

```
开发轴（内部）  里程碑 m-1a（开发线）  →  需求 R-gm-1a-0  →  任务 T-gm-1a-0-01
发布轴（对外）  对外版本 0.70（releases.yaml）  →  成员：需求 id 列表（多对多，可 backport）
```

- **里程碑必须由用户批准才能开**：先确认四要素——`id`（`m-<序号><代际字母>`，如 `m-1a`）、`alias`（意涵缩写，简短英文如 `self-host`，**不含版本号**）、定位（一句话）、`target`（目标日期）。不经许可不得擅开。
- **里程碑 = 开发线，不带版号**（两轴模型的开发轴）：卡 id 形态 `m-<序号><代际字母>`（`m-1a`）；**线段 = id 去 `m-` 前缀**（`1a`），需求的 id 就用它做第二段。版本号只出现在发版账（`releases.yaml`）。
- **开发线不排期版本，也不排条数**：线上可挂多条需求（线内序号自增），条数不限；**排没排满不构成结版障碍**（达成判据只认「关联需求全部验收通过」）；**不要为了「看起来整齐」改卡 id**——id 是线上全部需求的坐标根。
- **需求坐标 = 开发线**：建需求用 `gd req new "<标题>" --line 1a`，id 自动是 `R-<板>-1a-<线内序号>`，线内序号自增、不用手写；需求**不挂版本号**（版本 ↔ 需求的成员关系记在发版账）。
- **不跳层、不混轴**：需求挂开发线（线段就在 id 里），开发线归里程碑（卡本身就是线）；版本号归发版流程（`gd release`），需求不挂版本号。
- **三条「验收即结线」**：验收任务 = 结最小可交付单元（`check --pass`）；验收需求 = **结这条需求**（开发形态需求到此为止，子版坐标归发版账）；验收里程碑 = **结一条开发线**（`milestone reach`，**必须用户拍**）。存量板老格式需求验收时仍会自动结子版；`milestone reach` / `reopen` 擅自执行视同擅开。
- **需求回退不自动撤结版**：结版是宣告。存量板要让子版真的保持未结版，先把需求退回在途；要撤结版走 `ver reopen <x.y.z> --reason "…"`。
- **涉及开发线内容的规划，先出任务排表再动板**（`| 里程碑 | 需求 | 任务 | 优先级 |`），确认后才 `req new --line 1a` → `task add`。先落板后补表会让板上出现无规划的需求，改号与拆并都要动账。
- **开新里程碑前先写 bootstrap（规格），四要素只登记名字**：除了拍四要素（`id` / `alias` / 定位 / `target`），还要先落一份**里程碑 bootstrap**：`docs/gd-m<序号>-bootstrap.md`，七段式——**术语 / 场景 / 行为（编号规则）/ 待定（附「谁能否否」）/ 不该发生 / 暂不涉及 / 决定记录**。
  - **为什么**：四要素只说「这条线叫什么、大概做什么」，不说什么算做对；没有规格的里程碑只是一张待办卡。bootstrap 的「行为」段是可判定规则、「决定记录」段留了谁拍过什么。
  - **与排表的分工**：排表管**先后顺序**（谁做、先做哪个），bootstrap 管**什么算做对**。两者都先过用户。
  - **不追补**：只对新开与进行中的里程碑强制；**已达成 / 已归档的不补**（事后追认 = 第二套事实源）。
  - 口径全文：`entry/workflow/protocol.md` §3.6 第 8 条；样板：`docs/gd-m6-bootstrap.md`（m-6 首次采用）。

## 0.6 缺陷纪律（先分档，别一律立单）

发现缺陷**不许沉默跳过，也不许一律开单**。先判是不是缺陷（能复现吗 / 是预期行为吗？拿不准 ⇒ 按 T1 立单写清现象），再按体积分档：

| 档 | 判据 | 该做什么 |
|---|---|---|
| **T0 顺手修** | 不动契约 / 账格式 / 状态机 / 门禁 / core 闭包，≤ 3 文件 ≤ 30 行，不需新回归 | 就地修，同一提交带走；交付说明留一行「顺手修：<一句话>」。**不提需求、不建任务、不占开发线** |
| **T1 立缺陷单** | 跨模块 / 需回归 / 影响已结版 / 超 T0 体积 | `req new "<现象>" --kind bug --severity major\|minor --found-in <发现时版本>` → 拆任务 → 修在**当前在途开发线** |
| **T2 阻塞** | `blocker`，或影响**已发布**版本 | 立单标 `blocker`（结版门禁会拦）+ **立刻告知用户**；是否 backport 由人定（走发版账） |

**反范围蔓延**：修 T0 过程中一旦越界（要动第 4 个文件 / 触及契约 / 要补回归），立刻升档立单，不许把 T0 悄悄做成 T1。

**结版后发现缺陷** ⇒ 立新缺陷单（`found_in` 记已结版，不占开发线），不 reopen。

## 3. 模式闸（数据事实，不是配置）

`<板根>/seats/index.yaml` 存在 ⇒ **席位语义**：任务写面归席位自己的面（`gd seat task *`），owner 侧 `task add / handoff / check` 会被拒。
不存在 ⇒ **会话语义**：板主人直接在板上拆任务、交付、验收。
一条代码线，两种语义，切换只看这个文件在不在。

## 7. 边界（core 层不做的事）

不注册项目 · 不建席位 · 不起网页服务 · 不做 worktree 之外的 git 操作（提交/推送要显式命令）。
需要这些能力就装 app 层（完整 CLI + 席位 / 工作站）——core 面遇到这类命令会 exit 2 并指路，这是设计，不是缺陷。
