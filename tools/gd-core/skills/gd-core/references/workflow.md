# 两轴 workflow（开发轴 + 发布轴）与会话 SOP

## 1. 两轴账（开发轴：里程碑 → 需求 → 任务 · 发布轴：对外版本 → 需求成员）

| 层 | 命令 | 说明 |
|---|---|---|
| 里程碑 | `gd-core milestone add "…" --target <YYYY-MM-DD> --alias <意涵缩写>` | 开发线的载体（卡 id 铸 `m-1a`）；`alias` 只供人读检索，不参与排序 |
| 需求 | `gd-core req new "<标题>" --line <开发线段>` | 需求落**开发线**，id 自动 `R-<板>-<线段>-<线内序号>`（如 `R-gm-1a-0`）；**需求态由任务态派生**，不手改。`--ver <x.y>` / `--subver x.y.z` 是旧模型 / 存量口径，只给存量板用 |
| 任务 | `gd-core task add <需求id> --task "local:<标题>"` | 底层；`local` = 板内名册的执行体（会话 / 人的手） |
| 对外版本 | `gd-core release new/add/freeze/tag` | **发布轴账**（`releases.yaml`）：版本 ↔ 需求成员多对多（可 backport）；版本号只在这里产生，需求不挂版本号 |

编号规则：新模型需求 `R-<板id>-<线段>-<线内序号>`（如 `R-gm-1a-0`）· 旧模型 `R-<板id>-<版本段>-<子版号>` · 存量 `R-<板id>-001`；缺陷 `B-<板id>-<6位>`；任务 `T-<板id>-<线段>-<线内序号>-NN`。

**发布轴**（互不绑架）：`gd release new/list/show/add/freeze/tag` —— 版本号只在这里产生，成员表记「版本 ↔ 需求」（多对多，可 backport）。**开发线认领**：`gd line claim <线段> --as <名字>`（并行隔离；族名同 `gd-core`）。

**进行中可多张**：里程碑 `status` 是账面真值，写什么就是什么——多张可同时 `in_progress`（并行里程碑合法）；不派生、不接棒，达成一张不会改写别人的状态。并行隔离靠**开发线归属**（`gd line claim <线段> --as <名字>`，落 `lines.yaml`）。

**登记顺序（别踩坑）**：先有开发线 → 需求**落线**（`--line`，线内序号自增）→ 再拆任务。需求一旦全任务完成就进终态，之后再挂里程碑会被达成判据挡住（历史上真出过「无里程碑的孤儿需求」）。

## 2. 干一个任务的全链

```bash
gd-core work claim <任务id>        # 认领 = 这个动作：ready → in_progress，写占用租约（15 分钟，动账自动续期）
gd-core work start <任务id>        # 开隔离工作区：worktree + req/<需求id> 分支（主工作区零污染）
cd <工作区路径>                    # 在里面改代码
gd-core work submit <任务id>       # 精确路径提交 + rebase 到基线（冲突即停并回滚 rebase）
gd-core work land <任务id> --keep  # 串行 --ff-only 合入基线；**交件前别回收**（闸门第 5 条）
gd-core handoff <任务id> --done "<已做>" --artifact <件>   # 交件：有 done 无 remain ⇒ 一次到位进 review（在工作区里跑）
gd-core check <任务id> --pass --note "<结论>"              # 验收：review → done（同样在工作区里跑）
gd-core check <任务id> --reject "<原因>"                   # 打回：review → in_progress，原因入账
```

**闸门（别想抄近路）**：
- 未 `start` 不能 `submit`，未 `submit` 不能 `land`；
- `handoff --status done` 当场拒 —— 完成只能由 `check --pass` 产生；
- `check --pass` 只对 review 态生效；
- 别人持有的任务不能 `start`（租约过期才可接管，接管留痕）；
- **交件必须站在工作单元的分支上**（0.47 · B-gm-000022）：`handoff` 进 review 时要求 `task.work_unit` 存在，且**当前目录的分支 == 该单元分支**。所以 `land` 默认回收工作区 + 删分支之后，**回主仓交件会被拒**——这就是上面那条 `land --keep` 的由来。越过口是 `--direct`（落事件留痕）；`--force` 越不了这一条（它管占用抢占，一个旗标两种后果会让人顺手抢租约）。

**忘了 `--keep` 怎么办**：工作区已被回收（`land` 输出「工作区：已回收」）⇒ `gd work start <任务id>` 原地重开工作区 → `cd` 进去再交件。别用 `--direct` 绕过——那是「这次不隔离」的表态，不是回收的补救。
`land` 时你的 shell 正好在工作区里 ⇒ 工作区会自动保留（避免 cwd 指向已删除目录），并打印一行提示；**这种情况才不用 `--keep`**。

**交件的三条闸门（0.24.2 R-gm-087，别踩）**：
- **认领只归 `work claim`**：`handoff` 不再兼任认领——纯接手 / 只是宣告「我接手了」就走 `work claim`（它才有占用租约、才可被接管）。`handoff` 必须带 `--done` 或 `--remain` 至少一项，空交件当场拒；
- **未派不可交**：`executor` 空（没有承接方）的任务不能交件 —— 先定承接方（板面拆任务时带前缀 `local:标题`；席位面 `gd seat task dispatch`）；
- **他人占用拒**：任务正被别的会话持有且租约未过期 ⇒ 交件拒。等租约过期（无心跳自动可抢）· 让持有者 `work release` · 确需接管加 `--force`（原持有者会记进事件）。

**交件一次到位**：有 `done` 无 `remain` 直接进 `review`（合法流转表含 `ready → review` 的交件合一跃迁）。
旧口径「首次 handoff 只到 in_progress」已废——它会让 done / 交付件 / 事件**已经入账**、状态却还停在处理中，验收方按 `--to-check` 蹲不到单子，容易被误判成「没交件」。

**只做了一半**：只跑 `submit` 不跑 `land`，改动留在工作区里等下次接着做。

## 3. 交件四要素

`handoff` 的账字段：`done`（做成了什么，**可多次**）/ `remain`（还差什么，可多次）/ `decision`（为什么这么定，单值）/ `next`（下一步给验收的话，单值）。
`--decision` / `--next` 一次只给一条（重复给会被解析成空值）——多处取舍就合成一段写完。
`--artifact <件>` 会算指纹（sha256）入账 —— 交付事实与宿主无关，属 core。

### 3.1 证据充分性（软建议 · 不是闸门）

**前提**：验收人常常是**另一个会话**——它不共享干活时的上下文，只看得见「账 + 代码」。
所以「A 做、B 验」能不能独立成立，全靠交件时往账上放了什么；`check --pass` 不检查交件质量，这一条靠自觉。

交件侧（做的那个）自检：

| 要素 | 够用的写法 |
|---|---|
| `done` | 每条都能对上需求判据 / 任务口径，不写「已改好」 |
| `--artifact` | 改动落在哪些文件 / 目录就带哪些（指纹可复算；**指纹取自落地提交里的内容**，无提交可依时取工作树视图并在账上标 `source`） |
| `decision` | 取舍理由、被排除的做法、**隐含假设**——验收人最容易缺的就是这一段 |
| `next` | 明确告诉验收人往哪看、跑什么 |
| 顺序 | `land --keep` → **回工作区** `handoff` → 全部收尾后 `gd work sweep --apply` 回收；只 `submit` 的改动还在 `<代码仓>.wt/<需求id>`，验收人看到的是未入基线的状态 |

验收侧（验的那个）走法：读任务账 → 对判据逐条核 → 复算交付件指纹 → 重跑门禁 / 回归 → `check --pass --note`；
证据不够就 `check --reject "<缺什么>"`（回 `in_progress`、原因入账）。

**复算交付件指纹时问的是「成果还在不在」，不是「文件和交件时一不一样」**（0.70.6 · B-gm-000060）：
事实源是**落地提交**里那份内容——后续任务合法改动（改同一个文件 / 删掉它）动不了既成事实；
工作树里的未提交改动**不会**被 `land` 带走，与已交付内容无关。
两者都只提示、不拦；只有「账上指纹与落地提交里那份对不上，且没有后续提交能解释」（真失配）才拦（`E_ARTIFACT_STALE`）。

**别把「读不懂对方的意图」记成「对方没做完」**：先看 `decision` 段有没有写——缺了按证据不足 reject 要求补齐，比猜着 pass 便宜。

## 4. 两个概念别混

- `executor` = 负责人（长命、进账、板内名册里的名字）
- `claim` = 此刻谁在干（短命、带租约）

会话重启不丢「谁负责」；进程被 kill 也不会把任务锁死（租约过期即可被接管）。

## 5. 多会话并行：两件都要

账互斥（锁 + 租约 + 乐观锁重放）与代码隔离（worktree + 串行合入）**必须同时有**——
只做前者会出现「账不冲突，但两个人同时改同一个文件」。

**第一件事是先给这个 shell 一个固定会话号**（不是可选项）：

```bash
export GD_SESSION=w2        # 整轮固定（≤8 字符，中途别改）；认领/交件/交还都靠它认出「是同一个人」
export GD_EXECUTOR=w2      # 负责人（板内名册里的名字；与上面同名也无妨，但语义不同，见 §4）
gd-core line claim 1a --as w2     # 认领开发线（我的地盘；别人动这条线会被拒）
gd-core work next --claim          # 领下一个任务（我的线优先；没有则回报池空）
gd-core work start <任务id>
```

**不设会怎样（B-gm-000061，两条后果都只在「干到一半」时暴露）**：每条 `gd` 命令都是**独立进程**，
没会话号时会话退化成 `pid-<pid>` ——

- **挡自己**：上一条命令的占用，在下一条命令眼里是「他人持有」（`E_CLAIMED`）；
- **保不住活**：它**永远不会续期**（续期靠「同一会话再动账」），15 分钟后必然可被抢。

撞上了就两步：`export GD_SESSION=<固定短名>` → `gd-core work release <任务id> --force`（收回自己上一条命令的占用）。

`gd-core work next` 的挑选顺序：**我名下未过期的续作 → 我线上的 ready → 未认领线的 ready**；
派给别人的活不抢，他人开发线的活不领（领了也会被闸门拒）。

## 6. 结版是宣告，完成度是事实

开发轴的花板是 `gd milestone reach`（铁律：人拍）；发布轴的花板是 `gd release freeze → tag`（人拍）。
以下 `ver` 族是**存量兼容面**（老格式需求 ≡ 子版）：

```bash
gd-core ver list                              # 每条子版：完成度（派生） + 结版态（人的宣告）
gd-core ver reach <x.y.z> --confirm <x.y.z>   # 结版（须点名，铁律）
gd-core ver reopen <x.y.z> --confirm <x.y.z> --reason "<为什么之前的宣告有误>"
```

- **完成度**由需求状态派生；**结版**是人的宣告 —— 两件事分开显示，别混。
- 老格式需求验收时子版结版自动完成（不用单独拍）；开发形态需求（`R-<板>-<线段>-<n>`）没有子版这一步。
- `reopen` 的语义是「我之前的宣告有误」（漏了需求 / 验收结论被证伪），**不是**「又发现了 bug」——后者立新缺陷单（不占开发线）。
- 结版前若有未完成的 blocker 缺陷，会被门禁拦住（`--force` 才能越过，且要留痕）。
