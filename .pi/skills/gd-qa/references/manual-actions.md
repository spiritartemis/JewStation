# 必须人工验收的动作（单一事实源）

**判据**：这个动作一旦由 agent 代做，事后**无法从证据区分「人认了」还是「AI 猜了」**。
够这个判据的进清单；只是麻烦、不涉担责的，不进（那类由 agent 跑，人抽查）。

用法：用例里凡命中本表的，`人工项` 列填票号；跑测出件时按票号列出来交人。**agent 只出「依据 + 建议」，不代拍。**

## A1 · 里程碑结版（`reached`）

| 项 | 内容 |
|---|---|
| 动作 | `gd milestone reach <id>`（把这条大版本线宣告做完） |
| 为什么不能代 | 铁律：结版是「这条线做完了」的**宣告**，宣告错了要开 `reopen` 认错。机器只能证明「名下需求全 done」，证不了「这就是我们想交付的」 |
| 出处 | `entry/workflow/protocol.md` §3.6（`reach` = 人拍 · 铁律）· `reopen` 仅限「宣告有误」且 `--reason` 必填（§3.7.3） |
| agent 给什么 | 用例结论汇总 + 「具备/不具备结版条件」的判断与理由 + 未闭环项清单 |
| 人做什么 | 看过结版理由后自己跑 `reach`；不认可就让 agent 补跑或开 `reopen` |

## A2 · 开新里程碑（id / alias / 定位 / target）

| 项 | 内容 |
|---|---|
| 动作 | `gd milestone add …`（定 id、别名、这条线要解决什么、目标日期） |
| 为什么不能代 | 起名与定位是**产品的判断**，且里程碑 id 一旦落地，线上全部需求的坐标根就定了，改起来要动一堆 id |
| 出处 | 仓规「开里程碑须用户确认 id / alias / 定位（铁律）」· `protocol.md` §3.6（卡不带版号，版本号归发版账） |
| agent 给什么 | 候选 id / alias / 定位 / target 草案 + 与该仓既有卡 id 的撞号检查 |
| 人做什么 | 三个要素（id、alias、定位）逐项拍定后才落账 |

## A3 · 需求级验收（「这条需求算做完了」）

| 项 | 内容 |
|---|---|
| 动作 | `gd req verify <需求id>`（人工入口，TTY 确认）或验收人 `gd req acceptance sign` |
| 为什么不能代 | 需求级验收是**成品判断**：交付物存在且完整、与既有地基不冲突。任务级 `done` 只证明每件活干完了，证不了「合起来是对的」 |
| 出处 | `entry/workflow/reqflow.md` §5.7 验收 CLI（需求级留痕归用户；`trust: shared` 下席位身份需用户在场 `--by-user`）· `docs/task-lifecycle.md` 需求态表 |
| agent 给什么 | 判据逐条核对结果（哪条过、哪条过不了、证据在哪）+ 未回填项清单 |
| 人做什么 | 逐条认判据 ⇒ 授权 `--criteria-ok` 后签字；不认可则 `--reject "哪条判据没过"` |

## A4 · 判据（`criteria`）本身的确认

| 项 | 内容 |
|---|---|
| 动作 | `gd req acceptance set … --criteria "…"` 写下「怎么算过」 |
| 为什么不能代 | 判据写松了，后面所有「通过」都不可信；这是**验收的全部意义所在**，agent 自拟判据再自判 ⇒ 自证 |
| 出处 | `docs/gd-req-order-design.md` §2.2（③ 验收方法与结论分离） |
| agent 给什么 | 从需求描述推的判据草稿（可测、可观察、不含主观词） |
| 人做什么 | 改判据 or 认草稿；认了再让 agent 落账 |

## A5 · 主观面判断（好不好用 / 像不像样）

| 项 | 内容 |
|---|---|
| 动作 | 渲染观感、文案语气、交互顺不顺手、工位/工作站的游戏化体验是否成立 |
| 为什么不能代 | 这类结论没有可判据化的真值；机器能验「有这一段」，验不了「这一段对不对味」 |
| 出处 | 仓规 AGENTS.md §2「断言口径」（改菜单 / 动作文案不要新增文案断言——文案由渲染锚点与人工目视兜底） |
| agent 给什么 | 截图/输出原文 + 「机器能验到的部分」结论 + 明确的「未验项：观感」 |
| 人做什么 | 目视一遍，直接说改不改 |

## A6 · 口径裁定（这条算缺陷还是设计预期）

| 项 | 内容 |
|---|---|
| 动作 | 决定某个现象归 `真缺陷` / `设计预期`，以及缺陷定级（major / minor / blocker） |
| 为什么不能代 | 归错类比漏报更贵：`expected` 一多，报告就没人看了；`blocker` 一多，整条线被卡住 |
| 出处 | `protocol.md` §3.7.3（定级可改判；blocker 未完成不许结版） |
| agent 给什么 | 两三种归因各自的设计稿出处 + 后果推演（会挡结版 / 只是体验差） |
| 人做什么 | 拍归因与定级（必要时用 `gd req update … --severity` 改判） |

## A7 · 不可逆 / 破坏性动作

| 项 | 内容 |
|---|---|
| 动作 | 越过闸门（`--force`）、撤销需求（`gd req delete`）、回收工作区并删盘（`gd work sweep --apply`）、清理旧 work 块（`gd work migrate --prune-done`）、结版 / 重开 |
| 为什么不能代 | 这些是**已经拦过一次**的动作：闸门挡住的正是「现在不该做」。越过它需要有人对后果负责，且部分动作删掉的东西无法从账恢复 |
| 出处 | `protocol.md` §3.6 / §3.7.3 · 仓规禁止铁律（删改重要文件需确认） |
| agent 给什么 | 为什么被拦 + 越过后的具体后果 + 有没有非破坏性的替代路 |
| 人做什么 | 明确说「越过 / 不走这条路」；越过时自己跑，或在场看着 agent 跑 |

## A8 · 仓库外与凭据面

| 项 | 内容 |
|---|---|
| 动作 | `git push`、提交（未获授权时）、访问外部仓 / 服务、写本机布局（`gd.layout.yaml`）、动真实宿主端口与服务 |
| 为什么不能代 | 出了本机就没有回滚兜底；凭据与远端历史不是「改回来就行」的东西 |
| 出处 | 仓规禁止铁律（未经授权禁止 commit + push）· 布局注册属本机配置 |
| agent 给什么 | 待推清单（分支/提交数）+ 风险点 |
| 人做什么 | 授权一条明确的命令（范围写清），或自己执行 |

## A9 · 交付物的业务价值

| 项 | 内容 |
|---|---|
| 动作 | 判断黑盒产出「是不是我们想要的那个东西」（内容对不对、方向对不对） |
| 为什么不能代 | 验机制 ≠ 验内容；`gd` 能证明「件在、规格齐、流程通」，证不了「这份内容对我们有用」 |
| 出处 | `blueprint/e2e-acceptance.md` §一（总控不管设计；验收只查存在与完整性） |
| agent 给什么 | 交付件清单 + 与需求描述逐条比对的结果 |
| 人做什么 | 读成品，给「可用 / 要改哪一块」 |

## 人工动作票（交人时的写法）

```
人工项 A1 · 里程碑 m-4 结版
  依据：用例 10/10 pass（runs.md 2026-10-27 节）· 名下 34 需求全 done · contract check --scope all 绿
  建议：可以 reached
  人要做：确认「这是想交付的东西」后执行 gd milestone reach m-4
  留痕：milestones.yaml status: reached + 自动异地备份一次
```

票的三要素不许省：**依据（可复核）· 建议（明确一个方向）· 人要做的那一条命令**。
